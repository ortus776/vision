# Проверка просадки FPS при сборе данных

Подготовлены семь переключаемых вариантов в одной Release-сборке:
`build/windows-msvc/Release/pubg_vision_app.exe`. Можно открыть
`tools/test_collector.cmd` двойным щелчком и выбрать вариант в меню.
Тест длится 90 секунд с момента запуска сборщика, включая переключение окна
и паузы; F8 включает/приостанавливает сбор, F9 завершает раньше.
Launcher по умолчанию выбирает `png-store` — PNG без сжатия.
Обычный `--collect` без выбора варианта использует `balanced`.

## Запись игровых кадров и FPS в экспериментах

Launcher теперь автоматически запускает **PresentMon 2.6.0** для PID процесса,
которому принадлежит выбранное окно. Переносимый executable загружается из
официального GitHub-релиза в `build/tools/presentmon`, проверяется по SHA-256;
службы и драйверы не устанавливаются. Нужны Python 3 и оптимизированная Release-сборка.
Если PresentMon не запустился или не записал подходящие кадры, запуск завершается
ошибкой с сохранением частичных результатов, а не успешным отчётом с пустым FPS.
Если его журнал сообщает `Access denied`, запустите этот launcher из терминала
с правами администратора; скрипт сам не повышает права и не меняет группы Windows.

```powershell
# Та же сцена, настройки графики и характер нажатий; переключитесь в игру.
.\tools\test_collector.cmd -Variant baseline -WindowTitle "PUBG" -Seconds 90
.\tools\test_collector.cmd -Variant held -WindowTitle "PUBG" -Seconds 90
.\tools\test_collector.cmd -Variant png-store -WindowTitle "PUBG" -Seconds 90
python tools/analyze_experiment.py --compare data/performance
```

`baseline` запускает только монитор игровых кадров. Остальные варианты также
запускают сборщик с `--trace-frames`. Переключитесь в выбранное окно после старта;
первые 5 секунд исключаются из итогового замера (`-WarmupSeconds 5`). Паузы F8,
потеря фокуса, восстановление источника и завершающая запись очереди остаются
в исходных данных, но не входят в основной FPS активного сбора. В baseline фокус
проверяется раз в 100 мс; его точность ниже, чем у статусов самого сборщика.
Одинаковый PresentMon работает и в baseline, и в остальных вариантах.
Проводите несколько повторов, меняя порядок вариантов, и сравнивайте одинаковые
ROI, период снимков, длительность и сцену. Условия повторов скрипт не фиксирует.

Каждый запуск получает отдельную папку
`data/performance/<вариант>/run_<UTC>_<id>/`:

| Файл | Содержимое |
| --- | --- |
| `run.json` | PID, окно, вариант, параметры, QPC-частота и границы замера, хеш сборки, команды, коды завершения |
| `game_frames.csv` | Исходный PresentMon CSV: каждый зарегистрированный игровой кадр, CPU/GPU-метрики и режим вывода |
| `aligned_frames.csv` | Время каждого кадра, состояние сбора, включение в итоговый замер, пересечение с capture/acquire/map/copy/PNG/publish/очередью; ID запросов и пути PNG |
| `timeline.csv` | FPS, P95/P99 и длительности пересечений по секундным группам активного замера |
| `summary.json`, `summary.csv` | Средний FPS, P95/P99 frametime, 1% low, число кадров >16,67/>33,33 мс; сравнение кадров с пересечениями и без них |
| `collector/session_*/images/` | Реальные снимки датасета для обычных вариантов, PNG без потерь; у `png-store` без сжатия |
| `collector/session_*/collector_trace.jsonl` | QPC начала/конца стадий, статусы, связь с запросами и ID сохранённых изображений |
| `collector/session_*/events.jsonl`, `frames.jsonl`, `session.json` | Обычные журналы сессии, учёт снимков, ошибок и очередей |
| `presentmon.*.log`, `collector.log`, `run_trace.jsonl` | Диагностика запуска и завершения, отдельный журнал фокуса |

В корне сравнения появится `comparison.csv`. Повторный анализ конкретного запуска:

```powershell
python tools/analyze_experiment.py data/performance/png-store/run_...
```

Игровой кадр в анализе — интервал между соседними `CPUStartQPC` одной основной
swap chain. Она выбирается по числу строк; другие цепочки и PID учитываются
в диагностике, но не смешиваются с ней. Последняя строка не имеет следующего
времени и не образует интервал. QPC хранится как целое число, поэтому времена
игры и сборщика сопоставляются без потери точности или подгонки часов.
Средний FPS = `1000 / среднее время кадра`, 1% low = `1000 / среднее время
самых медленных ceil(1% × N) кадров`. P95/P99 — линейная интерполяция процентилей.
Это скорость CPU-кадров приложения; показанные кадры могут отличаться при
VSync, пропусках и генерации кадров. Исходные показатели отображения сохранены в CSV.

Время `png` включает encoder и запись временного файла на диск, `publish` —
переименование и frame manifest. `writer_queue` — задержка от окончания захвата
до начала encoder, включая проверки/публикацию запроса; это не CPU-нагрузка.
`acquire` включает ожидание обновления, `map` — ожидание доступности GPU readback.
Пересечение длинного игрового кадра с PNG или capture помогает найти зависимость,
но само по себе не доказывает причину: сравнивайте с `capture-only`, `input-only`
и baseline. Даже удерживаемый DXGI может влиять между отмеченными span.

Не создаются изображения на каждый игровой Present: это изменило бы нагрузку
эксперимента. Записываются тайминги каждого игрового кадра, а изображения — по
кликам и периодическому таймеру сборщика. `baseline`, `capture-only`, `input-only`
сохраняют игровые CSV, но не PNG. Трассировка сборщика пишет в отдельном потоке
через ограниченную очередь; `trace_dropped` явно показывает неполные данные.
У измерений есть собственная стоимость, поэтому сравнение проводится с тем же
монитором и включённой трассировкой. Прямой `--collect` не включает их автоматически.

Источник формата и ключей: [официальная документация PresentMon Console](https://github.com/GameTechDev/PresentMon/blob/main/README-ConsoleApplication.md).

Проверка реализации: Release собран, CTest 7/7. Отдельный тест создаёт
настоящую D3D11 swap chain и проверяет PresentMon, baseline, PNG, паузу F8,
возобновление, ранний F9, отсутствие потерь трассы и ссылки CSV на изображения:

```powershell
python tests/manual/experiment_smoke.py
```

В последнем таком прогоне сохранены 25 PNG и 282 интервала активного сбора,
пауза отделена от основного замера, валидатор сессии не нашёл ошибок. Это проверка
работы измерений на тестовом окне, а не замер PUBG. Артефакты:
`build/experiment-smoke-1791110466010313700/`. Автоматические проверки также
покрывают точность QPC выше 2^53, несколько swap chain, процентиль/FPS/1% low,
границы пауз и span, очередь трассы, временную блокировку `run.json` читателем,
WIC и несжатый PNG в путях длиннее 260 символов. Запись сессии использует
расширенные пути Windows, поэтому вложенность экспериментальных папок
не требует включать системную настройку длинных путей.

## Что найдено в коде

1. Раньше `copy_desktop_crop()` освобождал DXGI-кадр сразу после снимка,
   а следующий снимок мог быть через несколько секунд. `DuplicateOutput()`
   оставался активным даже до первого F8 и после паузы. По документации
   Microsoft, между освобождением и получением кадра ОС копирует обновления
   рабочего стола в поверхность duplication, расходуя GPU. Собственный crop
   640×640 ограничивает только копирование ROI в staging texture;
   это не ограничение размера поверхности duplication.
2. После `CopySubresourceRegion()` сразу вызывается блокирующий `Map()`.
   CPU ждёт завершения GPU-копирования. Таймаут `next(5)` ограничивает
   ожидание `AcquireNextFrame`, но не весь вызов и не `Map`.
3. PNG сохраняются отдельным потоком, однако сжатие всё равно потребляет
   CPU и пропускную способность памяти. На каждый снимок создаются COM/WIC
   объекты. Частые отдельные нажатия ЛКМ создают серии 0/100/200 мс;
   общего ограничения частоты снимков сейчас нет. Удержание ЛКМ само по себе
   не создаёт новую серию на каждый выстрел.
4. Проверка геометрии окна раньше выполнялась на каждой итерации,
   в том числе при пробуждениях от движения мыши. `events.jsonl` записывается
   синхронно с `flush()` под mutex. В прежних локальных замерах журнал был
   дешёвым, поэтому это вторичный кандидат; теперь время журнала измеряется
   в каждой сессии. Нейросеть и overlay в `--collect` не запускаются.
5. В существовавшем `build/windows-msvc/CMakeCache.txt` были пусты
   `CMAKE_CXX_FLAGS_RELEASE`; команды `CL.command.1.tlog` подтверждают
   отсутствие `/O2`. Название конфигурации Release не гарантировало
   оптимизированный машинный код. В preset теперь явно задано
   `/O2 /Ob2 /DNDEBUG`; сборка выполнена повторно.

Это кандидаты на причину падения 90–110 → 40–50 FPS, а не доказанный диагноз:
игровые FPS здесь не измерялись.

## Варианты и сравнения

| Вариант | Поведение | Что сравнивать |
| --- | --- | --- |
| `legacy` | Исходное раннее освобождение кадра, DXGI остаётся при паузе, частые проверки окна | Исходная точка сравнения |
| `balanced` | Раннее освобождение; DXGI создаётся только при включённом сборе и фокусе, уничтожается при паузе/потере фокуса; геометрия проверяется раз в 100 мс и до/после снимка | С `legacy`: жизненный цикл и проверки окна |
| `held` | Как `balanced`, но владение кадром сохраняется до следующего acquire | С `balanced`: лишние desktop-копирования |
| `png-none` | Как `held`, но PNG с `WICPngFilterNone` | С `held`: выбор PNG-фильтра; качество сохраняется, размер/скорость могут измениться |
| `png-store` | Как `held`, но PNG без сжатия: DEFLATE stored blocks, filter 0, без WIC-компрессора | С `held`: устранение сжатия при сохранении совместимости PNG |
| `capture-only` | Как `held`, снимок считывается в RAM, изображения и frame manifest не сохраняются | С `held`: совокупная стоимость PNG и записи изображений |
| `input-only` | Raw Input, hotkeys, scheduler и журнал; DXGI не создаётся, снимков нет | С `capture-only` и игрой без программы: влияние захвата и ввода |

`balanced` — новый вариант по умолчанию. `held` оставлен отдельным экспериментом:
другие проекты отмечают возможные проблемы со временем ожидания/плавностью
при позднем освобождении кадра. `legacy` воспроизводит прежний рабочий путь,
но также содержит новую лёгкую телеметрию, оптимизацию `/O2` и освобождение
источника перед завершающим ожиданием PNG-потока. Для отдельного сравнения
оптимизации сохранён предыдущий executable:
`build/collection-variants-results/pubg_vision_app_before_O2.exe`.

**`capture-only` и `input-only` не собирают датасет.** Это явно отмечено
в консоли и `session.json`; каждый запрос получает итог `skipped` с
диагностической причиной. Формат сессии и проверка учёта запросов сохраняются.

## Запуск

Из корня проекта:

```powershell
.\tools\test_collector.cmd -Variant legacy -WindowTitle "PUBG" -Seconds 90
.\tools\test_collector.cmd -Variant balanced -WindowTitle "PUBG" -Seconds 90
.\tools\test_collector.cmd -Variant held -WindowTitle "PUBG" -Seconds 90
.\tools\test_collector.cmd -Variant capture-only -WindowTitle "PUBG" -Seconds 90
.\tools\test_collector.cmd -Variant input-only -WindowTitle "PUBG" -Seconds 90
.\tools\test_collector.cmd -Variant png-none -WindowTitle "PUBG" -Seconds 90
.\tools\test_collector.cmd -Variant png-store -WindowTitle "PUBG" -Seconds 90
```

Укажите подстроку настоящего заголовка окна. Найти его можно так:

```powershell
.\build\windows-msvc\Release\pubg_vision_app.exe --list-windows
```

Дополнительные параметры launcher: `-RoiWidth`, `-RoiHeight`, `-PeriodicMs`,
`-Exe`, `-WarmupSeconds`, `-GameProcessId`. Последний проверяет, что выбранное
окно принадлежит ожидаемому PID. `-Exe` должен поддерживать `--trace-frames`.
Сохраните одинаковый ROI и интервал для всех сравнений.
Прямой запуск без launcher:

```powershell
.\build\windows-msvc\Release\pubg_vision_app.exe --collect --start-active --window-title "PUBG" --collect-variant png-store --collect-seconds 90 --output data/performance/png-store
```

Сначала измерьте игру вариантом `baseline`, затем `legacy`,
`balanced`, `held`, `capture-only`, `input-only`, `png-store` и `png-none`.
Желательно повторить основные сравнения три раза, чередуя порядок.
Используйте один игровой режим, похожий участок, одинаковое число отдельных
нажатий ЛКМ, настройки, питание и прогрев. Игровой FPS и 1% low теперь
сохраняет launcher через PresentMon. Счётчики самого сборщика по-прежнему
описывают снимки и не выдаются за FPS игры.

В отдельном прогоне проверьте FPS после F8 и после F9. В `legacy` F8
оставляет DXGI открытым; в остальных вариантах захвата F8 уничтожает DXGI,
но уже принятые PNG ещё дописываются. Дайте очереди несколько секунд
на завершение, прежде чем делать вывод по FPS на паузе.

Если `held` заметно лучше `balanced`, это поддерживает гипотезу лишних
копирований desktop. Если `capture-only` лучше `held`, существенны PNG/диск.
Если даже `capture-only` сильно снижает FPS, а `input-only` — нет,
дальше проверять DXGI/readback и альтернативный backend Windows Graphics
Capture. Если `input-only` тоже влияет, проверить Raw Input, частоту мыши
и журнал. Размер ROI можно уменьшать отдельным экспериментом, после
сравнения вариантов с одинаковыми настройками.

## Результаты и телеметрия

Сессии launcher: `data/performance/<variant>/run_*/collector/session_*`. Каждые пять секунд
и после дописывания PNG в `events.jsonl` появляется `collection_performance`.
Счётчики накопительные с начала сессии. Итоговый `session_finished` остаётся
последним событием, как требует валидатор.

```powershell
python tools/summarize_collection.py data/performance
python tools/validate_session.py data/performance/held/run_.../collector/session_...
```

CSV показывает количество снимков и сохранений, таймауты и пропуски,
среднее/максимальное время `next`, `Map`, PNG, глубину очереди,
время обработки ввода, проверок окна и журнала. `acquire_mean_ms` включает
ожидание новых desktop-обновлений; это не чистая стоимость GPU.
`process_cpu_ms` — суммарное CPU-время процесса по Windows, не загрузка GPU.
Последняя запись включает время дописывания очереди после остановки.
GPU-копирования ОС между вызовами не видны в этих CPU-замерах: для их
подтверждения нужны игровые FPS и при необходимости отдельный GPU-профиль.

## Несжатый PNG и будущий инференс

`png-store` пишет полноценный RGBA PNG, но не ищет повторяющиеся данные
и не выполняет энтропийное сжатие: DEFLATE использует только stored blocks.
Сохраняются все каналы и значения пикселей. Происходит преобразование
порядка каналов BGRA → RGBA для файла; при чтении в BGRA исходные байты
восстанавливаются. Контрольные суммы CRC32 и Adler32 остаются обязательными
частями формата. Для них используются таблицы CRC и блоковое вычисление
Adler; IDAT записывается одним большим блоком.

PNG 640×640 занимает **1 639 233 байта** (1,56 MiB), 1280×1280 —
6 555 448 байт (6,25 MiB), независимо от содержания. При 10 снимках/с
640×640 это примерно 16,4 MB/с и 0,98 GB/мин только изображений.
Сложные кадры могут увеличиться умеренно относительно сжатых PNG;
однородные изображения — во много раз. Код использует два временных
буфера приблизительно по размеру BGRA-кадра в потоке записи.

Обычный PNG тоже **сжимается без потерь**. При одинаковом декодировании
и preprocessing модель получает те же пиксели из сжатого и несжатого PNG.
Сжатие PNG само по себе не создаёт расхождения между обучением и инференсом.
Причина отказаться от него в сборщике — время CPU и влияние на игру.
Для живого инференса `core::Frame::pixels` уже содержит несжатый BGRA;
сохранять/читать PNG перед вызовом модели не требуется.

## Выполненные проверки, 03.10.2026

- MSVC x64 Release собран, CTest: 6/6 успешно.
- Проверены все семь вариантов на синтетическом окне: F8, сворачивание,
  resize, закрытие/повторное открытие, смена монитора, остановка.
  Сессии вариантов и отдельная сессия auto-stop прошли `validate_session.py`.
  Проверено, что `input-only` имеет ноль вызовов prepare/capture,
  а `capture-only` захватывает кадры и не пишет PNG.
- Удержание кадра проверено настоящим DXGI на двух мониторах: повторные
  acquire, изменение ROI, reset, повторное создание. Оба PNG-фильтра
  декодированы WIC и сравнены побайтно с исходными BGRA-пикселями.
- PNG microbenchmark: градиент/шум, 320/640/1280, два фильтра,
  по 20 измерений после трёх прогревочных вызовов. В первом прогоне, до
  восстановления `/O2` в CMake-кэше,
  шумный 640×640: среднее 43,18 мс default, 37,90 мс none;
  градиент 640×640: 8,18 и 13,45 мс соответственно.
  Поэтому отключение фильтра не объявляется универсальным ускорением.
  Синтетический шум не является игровым изображением; первый прогон
  частично совпал с другими локальными проверками.
- Несжатый PNG дополнительно проверен независимым Python/zlib-декодером:
  CRC, Adler32, каналы/alpha, границы DEFLATE-блоков 65535 байт и
  кратные им размеры. Проверены некорректные буферы и ошибки открытия файла.

Итоговый прогон после включения `/O2`, без параллельного запуска других
локальных тестов: среднее время полного вызова encoder, включая создание
и запись файла, на синтетическом шуме:

| ROI | Сжатый WIC PNG, мс | PNG без сжатия, мс | Размер несжатого PNG |
| --- | ---: | ---: | ---: |
| 320×320 | 15,65 | 6,08 | 410 018 B |
| 640×640 | 38,30 | 7,77 | 1 639 233 B |
| 1280×1280 | 124,67 | 15,07 | 6 555 448 B |

Для шумного 640×640 получилось примерно **4,9× быстрее**; сжатый файл
занимал 1 434 991 B, увеличение размера — около 14%. Однако градиент
640×640 сохранялся за 7,04 мс с WIC и 8,76 мс без сжатия: на простых
изображениях меньший размер файла может перевесить стоимость компрессора.
Частоты, температуры и все фоновые задачи ОС не контролировались;
это локальный benchmark, не обещание такой же скорости в игре.
CPU-время потока в CSV имеет грубую дискретность Windows.

После пересборки с `/O2` повторно пройдены CTest 6/6, held capture на двух
мониторах и smoke `png-store`. Последний сохранил 20 изображений без
ошибок writer и без переполнения очереди; сессия прошла валидатор.
ROI этого smoke — 320×240 с однотонным содержимым, его среднее время
encoder 1,65 мс не следует сравнивать с шумным 640×640 из таблицы.
Первые smoke остальных вариантов выполнялись до включения `/O2`.
Флаги финальной компиляции подтверждены в `CL.command.1.tlog`.

## Проверенные внешние источники

- [Microsoft: ReleaseFrame](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_2/nf-dxgi1_2-idxgioutputduplication-releaseframe)
  — рекомендация освобождать перед следующим acquire и описание лишних GPU-копирований.
- [Microsoft: AcquireNextFrame](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_2/nf-dxgi1_2-idxgioutputduplication-acquirenextframe)
  — таймаут, pointer-only updates, обязательное освобождение прошлого кадра.
- [DXcam: dxgi_duplicator.py](https://github.com/ra1nty/DXcam/blob/main/dxcam/core/dxgi_duplicator.py)
  — поддержка владения кадром и пояснение выбора раннего release из-за
  наблюдавшихся проблем с аудио и frame pacing.
- [OBS: d3d11-duplicator.cpp](https://github.com/obsproject/obs-studio/blob/master/libobs-d3d11/d3d11-duplicator.cpp)
  — `AcquireNextFrame(0)`, копирование в собственную GPU-текстуру и ранний
  release; этот видеопуть отличается от нашего редкого CPU-readback.
- [Lightpack: обсуждение PR #373](https://github.com/psieg/Lightpack/pull/373)
  — практическое обсуждение влияния порядка release/acquire, включая
  наблюдение падения игрового FPS; не доказательство причины в этом проекте.
- [Microsoft: WIC PNG options](https://learn.microsoft.com/en-us/windows/win32/wic/png-format-overview)
  — настройка `FilterOption` через `IPropertyBag2`.

- [W3C: PNG specification](https://www.w3.org/TR/png-3/)
  — формат без потерь, RGBA и контрольные суммы.
- [RFC 1951: DEFLATE](https://www.rfc-editor.org/rfc/rfc1951.html)
  и [RFC 1950: zlib](https://www.rfc-editor.org/rfc/rfc1950.html)
  — несжатые блоки и оболочка zlib с Adler32.

Внешний код не копировался; варианты реализованы в текущем C++-источнике.
